# 실손보험 청구 서류 검증 (가칭) — 기능명세서

> 해커톤 MVP 기준. 심사 기준(데이터 40 · 워크플로우 50 · 서비스 10)에 맞춰 설계했다.

## 0. 개요

### 0.1 한 줄 정의

실손보험 청구 서류 묶음을 **두 가지 방법으로 읽고, 영수증 안의 검산식으로 맞는 값을 골라내고, 오류 원인을 읽기 오류·서류 불일치·서류 누락으로 나눠** 심사 담당자가 할 일까지 알려주는 워크플로우.

### 0.2 사용자

**보험사 청구 접수·심사 담당자.** 실손24 같은 전산 연계 없이 종이·이미지·PDF로 들어오는 청구 서류를 받아, 심사를 진행할지, 고객에게 보완을 요청할지 정한다.

담당자가 지금 겪는 문제: OCR이 값을 읽어 주지만 틀린 값도 자신 있게 내놓기 때문에, 결국 원본을 다시 읽어야 한다.

### 0.3 하는 것과 하지 않는 것

| 하는 것 | 하지 않는 것 |
| --- | --- |
| 서류에 적힌 값을 정확히 읽었는지 검증 | 보험금 계산, 지급·거절 판단 |
| 서류끼리 금액·날짜·이름이 맞는지 검증 | 의학적 판단 (진단과 치료가 적절한지) |
| 청구 유형에 필요한 서류가 다 있는지 확인 | 보험사기 판단 |
| 같은 서류가 두 번 들어왔는지 확인 | 약관 해석, 실손 세대별 보장 판단 |

판정은 모두 `확정 / 불일치 / 검토 필요` 같은 정해진 값으로만 낸다. 위험도 점수나 확률은 내지 않는다.

### 0.4 용어

| 용어 | 뜻 |
| --- | --- |
| 청구 묶음 (Claim) | 한 번의 청구로 들어온 서류 전체 |
| 영수증 | 진료비 계산서·영수증 (법정 서식) |
| 세부내역서 | 진료비 세부산정내역서 |
| 경로 A | 표 구조를 읽어 서식의 칸 위치로 값을 찾는 추출 |
| 경로 B | LLM으로 "본인부담금은 얼마인가"처럼 의미로 값을 찾는 추출. F2의 OCR 결과를 쓰지 않고 원본 파일을 따로 읽는다 |
| 검산식 | 영수증 안이나 서류 사이에서 숫자끼리 맞아야 하는 관계 (§3) |
| 확정 값 | 검증을 통과해 믿을 수 있다고 정한 값 |
| 이슈 (Issue) | 검증에서 나온 문제 하나. 원인, 관련 칸, 근거를 가진다 |
| 결론 | 청구 묶음 하나에 대한 최종 정리: `심사 진행 가능 / 보완 요청 / 검토 필요` |

### 0.5 처리 흐름

```
F1 입력 ─┬→ F2 파싱(OCR) → F3 분류 ─┬→ F4 경로 A: F2의 표에서 칸 찾기 ─┐
         │                          │                                 ├→ F6 값 확정 ─→ F7 문서 간 검증 ─┐
         └──── 원본 파일 ───────────┴→ F5 경로 B: 원본을 직접 읽기 ───┘   (검산식)    F8 누락 검사      ├→ F10 원인 분류·결론 → F11 결과 리포트
                                                                                      F9 중복 검사 ─────┘
                 └──────────────── 어느 단계든 판단할 수 없으면 F12 '검토 필요'로 ────────────────┘
```

| 단계 | 이 순서인 이유 |
| --- | --- |
| 분류를 추출보다 먼저 | 문서 종류마다 서식과 뽑을 칸이 달라서 |
| 추출을 두 경로로 | 한 경로가 자신 있게 틀려도 다른 경로와 어긋나서 드러나게 하려고 |
| 경로 B는 원본을 따로 읽기 | 두 경로가 같은 OCR 결과를 보면 글자를 잘못 읽은 오류(3 → 6)를 같이 틀려서, 어긋남이 생기지 않는다 |
| 값 확정을 문서 간 검증보다 먼저 | 값이 확정되기 전에 서류끼리 비교하면, 읽기 오류가 서류 불일치로 잘못 나와서 |
| 판정을 코드 규칙으로 | 산술 비교라 LLM에 맡기면 다시 돌릴 때 결과가 흔들려서 (실행 정확도) |

## 2. 기능 상세

### F1. 청구 묶음 입력

| 항목 | 내용 |
| --- | --- |
| 입력 | 서류 파일 1~10개 + 청구 정보(청구 유형: `통원 / 입원 / 약제`) |
| 형식 | PNG, JPG, PDF |
| 선택 입력 | 이전 청구 목록 JSON (F9 중복 검사용) |
| 출력 | `claim_id`, 파일 목록 |

- 청구 유형이 없으면 서류 구성으로 추정하고, 추정이 애매하면 `검토 필요`로 둔다.

### F2. 문서 파싱·OCR

| 항목 | 내용 |
| --- | --- |
| 처리 | 글자, 표(행·열·셀), 레이아웃을 뽑는다 |
| 출력 | 문서마다 `blocks[]`: 블록 id, 종류(문단·표·셀), 텍스트, 페이지, 좌표, OCR 신뢰도. 표는 행·열 번호 포함 |

- 모든 이후 단계는 **블록 id로 원문 위치를 가리킨다.** 리포트의 원문 위치 표시가 여기서 나온다.
- 이미지가 잘렸거나 표가 페이지 밖으로 나간 것으로 보이면 `CROPPED` 표시를 붙인다.

### F3. 문서 유형 분류

| 값 | 문서 |
| --- | --- |
| `receipt` | 진료비 계산서·영수증 (별지 제6호·제7호서식), 한방진료비 계산서·영수증 (제8호·제9호서식) |
| `simple_receipt` | 간이 외래 진료비 계산서·영수증 (제12호서식, 수기용) |
| `itemized_bill` | 진료비 세부산정내역서 |
| `pharmacy_receipt` | 약제비 계산서·영수증 (제10호·제11호서식) |
| `payment_cert` | 진료비(약제비) 납입 확인서 (제12호의2서식) |
| `prescription` | 처방전 |
| `diagnosis` | 진단서, 소견서 |
| `visit_cert` | 통원확인서, 입퇴원확인서 |
| `other` | 그 외 (카드 전표, 본인부담금 수납대장, 요양급여대상 확인 신청서, 식당 영수증 등) |

- 유형과 함께 서식 번호(`form_no`)도 낸다. 서식마다 칸 번호와 검산식이 달라서다(§3).
- 신뢰도가 기준 미만이거나 두 유형 점수가 비슷하면 `UNKNOWN_DOC`으로 `검토 필요`.
- 카드 결제 전표는 `other`로 분류하고, 영수증을 대신할 수 없다는 이슈를 만든다.

### F4. 경로 A: 표 위치 기반 추출

| 항목 | 내용 |
| --- | --- |
| 입력 | F2의 표 구조, F3 유형 |
| 처리 | 서식의 행 이름(예: "주사료", "합계")과 열 이름(예: "본인부담금")을 찾아, 그 교차 셀의 값을 읽는다 |
| 출력 | 필드마다 값, 근거 셀 블록 id, OCR 신뢰도 |

- 행·열 이름은 **동의어 표**로 맞춘다. 예: "투약및조제료" = "투약 및 조제료", "처치및수술료" = "처치·수술료".
- 표를 찾지 못하거나 행·열 이름을 맞추지 못하면 그 필드는 `null`. 추측하지 않는다.
- 별지 제7호서식은 표 선 없이 괄호 칸으로 인쇄된다. 표 구조가 안 잡힐 수 있으므로 행·열 이름의 좌표로도 칸을 찾는다.

### F5. 경로 B: 의미 기반 추출

| 항목 | 내용 |
| --- | --- |
| 입력 | **원본 파일**, F3 유형. F2의 OCR 결과는 쓰지 않는다 |
| 처리 | 유형별 추출 스키마로 원본을 직접 읽어 값을 뽑는다. 필드 설명에 서식상 위치와 다른 이름을 적어 둔다 |
| 출력 | 필드마다 값, 근거 인용문, 근거 위치(도구가 주면) |

- **왜 원본을 따로 읽나**: 경로 A는 F2의 OCR 결과를 쓴다. 경로 B까지 같은 OCR 결과를 보면, F2가 흐린 3을 6으로 읽었을 때 두 경로가 똑같이 36,000을 내서 어긋남이 생기지 않는다. 글자 읽기부터 따로 해야 두 경로 비교(F6)가 의미가 있다.

| | 같은 OCR 공유 | 원본을 따로 읽기 |
| --- | --- | --- |
| 칸을 잘못 짚는 오류 | 잡음 | 잡음 |
| 글자를 잘못 읽는 오류 (3 → 6) | 못 잡음 | 잡음 |

- temperature 0.
- 경로 B의 값이 F2 텍스트와 다르다고 버리지 않는다. 다른 것이 정상일 수 있고, 어느 쪽이 맞는지는 F6이 검산식으로 정한다. LLM이 지어낸 값도 F6 검산식에서 걸러진다.
- 근거 위치는 도구가 좌표를 주면 그것을 쓰고, 주지 않으면 경로 A가 찾은 같은 필드의 셀 위치를 쓴다.
- 경로 A와 **같은 필드 목록**을 쓴다(§4.1).
- Upstage Extract가 Document Parse와 같은 OCR 엔진을 쓰면 두 경로가 같이 틀리는 경우가 늘어난다. 확인하고, 필요하면 경로 B를 다른 방식(예: 이미지를 직접 받는 비전 LLM)으로 바꾼다(§9 Q9).
- 두 경로가 같이 틀리는 경우가 완전히 없어지지는 않는다. 그때는 F6에서 `INTERNAL_MISMATCH`로 빠지므로 틀린 값을 믿고 넘기지는 않는다.

### F6. 두 경로 비교와 값 확정 (핵심)

필드마다 아래 순서로 값을 정한다. 규칙은 코드로 구현한다.

**1단계: 두 경로 비교**

| 경우 | 처리 |
| --- | --- |
| A = B | 후보 하나. 2단계 검산식 확인으로 |
| A ≠ B | 후보 둘. 2단계에서 검산식으로 고른다 |
| 한쪽만 값이 있음 | 후보 하나. 2단계 검산식을 **반드시** 통과해야 확정 |
| 둘 다 없음 | `MISSING_FIELD` → `검토 필요` |

**2단계: 검산식으로 확정** (§3의 영수증 금액 칸 검산식 C1~C6만 쓴다)

검산식을 쓸 수 있는 조건: **그 식에 들어가는 다른 값들이 모두 A = B로 일치**해야 한다. 기준이 되는 숫자까지 흔들리면 어느 쪽이 맞는지 판단할 수 없기 때문이다.

| 경우 | 처리 | 근거로 남기는 것 |
| --- | --- | --- |
| A = B이고 관련 검산식 모두 통과 | **확정** | `agree` + 통과한 검산식 |
| A = B인데 관련 검산식이 깨짐 | `검토 필요` (`INTERNAL_MISMATCH`). 두 경로가 같이 틀렸거나, 서류 자체가 틀렸을 수 있다 | 깨진 검산식 |
| A ≠ B이고 한쪽만 검산식 통과 | 통과한 쪽으로 **확정** | `checksum` + 검산식 id |
| A ≠ B이고 둘 다 통과 | `검토 필요` (`AMBIGUOUS_VALUE`) | |
| A ≠ B이고 둘 다 실패 | `검토 필요` (`READ_CONFLICT`) | |
| 검산식에 쓰이는 다른 값이 A ≠ B | `검토 필요` (`UNSTABLE_BASE`) | 흔들린 기준 값 |
| 이름에 가려진 글자(`*`)가 있음 | 가려진 자리를 빼고 나머지 글자가 같으면 일치로 본다. 확정 값은 **가려진 쪽**(예: `김*수`)으로 둔다. 서류에 없는 글자를 채워 넣지 않기 위해서다 | `agree` |
| 검산식이 없는 필드(이름, 날짜, 기관명 등) | A = B면 확정, 아니면 `검토 필요` (`READ_CONFLICT`) | |

**예시**

| 필드 | 경로 A | 경로 B | 비고 |
| --- | --- | --- | --- |
| 본인부담금 합계 | 35,000 | 36,000 | 불일치 |
| 공단부담금 합계 | 65,000 | 65,000 | 일치 (기준으로 쓸 수 있음) |
| 전액본인부담 합계 | 0 | 0 | 일치 (기준으로 쓸 수 있음) |
| 비급여 합계 | 150,000 | 150,000 | 일치 (기준으로 쓸 수 있음) |
| 진료비 총액 | 250,000 | 250,000 | 일치 (기준으로 쓸 수 있음) |

검산식 C1 (진료비 총액 = 본인부담금 + 공단부담금 + 전액본인부담 + 비급여):
- A: 35,000 + 65,000 + 0 + 150,000 = 250,000 ✅
- B: 36,000 + 65,000 + 0 + 150,000 = 251,000 ❌

→ **35,000(경로 A) 확정**, 근거 `checksum: C1`.

항목 행의 금액은 끝수처리 때문에 정확히 검산할 수 없다(§3 S1). 두 경로가 같으면 확정하고, 다르면 `READ_CONFLICT`로 둔다.

**3단계: 확정 실패 처리**

- 확정하지 못한 필드는 값을 비워 두고, 두 후보와 이유 코드를 함께 남긴다. 담당자가 원본에서 그 칸만 보면 되게 한다.
- OCR 신뢰도가 기준 미만인 셀에서 나온 값은 1·2단계를 통과해도 확정하지 않는다(`LOW_OCR`).

### F7. 문서 간 검증

**F6에서 확정된 값끼리만** 비교한다. 확정되지 않은 값이 끼면 비교하지 않고 `검토 필요`로 둔다. 이렇게 해야 읽기 오류가 서류 불일치로 잘못 나오지 않는다.

| 규칙 | 비교 | 불일치 조건 |
| --- | --- | --- |
| X1 | 세부내역서 합계 행의 본인부담금·공단부담금·전액본인부담·비급여 ↔ 영수증 ①②③④ | 금액이 다르다 |
| X2 | 세부내역서 총액의 합계 ↔ 영수증 ⑥ 진료비 총액 | 금액이 다르다 |
| X3 | 서류끼리 환자 이름 | 다르다 |
| X4 | 서류끼리 진료일·진료 기간 | 영수증 진료 기간 밖의 날짜가 있다 |
| X5 | 서류끼리 요양기관 | 다르다 |
| X6 | 처방전 발행일 ↔ 약제비 영수증 조제일 | 조제일이 처방전 유효 기간 밖이다 |

- 이름은 가운데 글자를 가린 경우(홍*동)를 허용한다. 가려진 글자 외에 다르면 불일치. F6과 같은 규칙이다.
- 불일치마다 양쪽 값, 차이 금액, 양쪽 근거 위치를 남긴다.
- 세부내역서는 `계`가 아니라 끝수처리를 반영한 `합계`로 비교한다.
- 항목 행끼리는 불일치로 판정하지 않는다. 같은 금액이 세부내역서에서는 치료재료대, 영수증에서는 선별급여 행에 들어가는 경우가 있다.

### F8. 서류 누락 검사

청구 유형과 확정 값으로 필요한 서류를 정하고, 묶음에 없으면 이슈를 만든다. **규칙은 코드가 아니라 표(설정 파일)로 둔다.** 보험사마다 기준이 달라도 표만 바꾸면 된다.

| 규칙 | 조건 | 필요한 서류 |
| --- | --- | --- |
| D1 | 모든 청구 | 영수증, 간이 영수증 또는 약제비 영수증 |
| D2 | 통원이고 동일 사고당 영수금액이 3만 원 초과 | 질병분류기호가 적힌 처방전 |
| D3 | 통원이고 10만 원 초과 | 추가 증빙(진단서, 통원확인서, 진료확인서, 소견서, 진료차트 등)이 **필요할 수 있음** → 없으면 `NEEDS_REVIEW` |
| D4 | 산부인과, 항문외과, 비뇨기과, 피부과 통원 | 3만·10만 원 간소화 기준 적용 안 함 → 추가 증빙이 없으면 `NEEDS_REVIEW` |
| D5 | 입원 | 영수증 + 세부내역서 + 진단서. 50만 원 이하는 진단서 대신 진단명이 있는 입·퇴원 확인서, 또는 진단명과 입원기간이 있는 진료확인서 가능 |

- 기준: [손해보험협회 실손의료보험금 청구서류 표준안](https://consumer.knia.or.kr/m/consumer/insurance-guide/0202.do) (2014. 1. 1. 시행, 손해·생명보험사 공통). 보험사와 상품, 사고 내용에 따라 추가 서류를 요구할 수 있다.
- 3만 원 이하 통원은 보험금 청구서에 진단명이 있어야 한다. 표준안의 공통 서류(보험금 청구서, 신분증 사본)는 MVP 검사에서 제외한다(§9 Q1).
- 표준안에는 통원 세부내역서와 약제비 항목이 없다. 비급여 통원의 세부내역서는 누락으로 판정하지 않고, 있을 때만 문서 간 검증(F7)에 쓴다(§9 Q1).
- 조건에 쓰는 값(비급여 금액 등)이 확정되지 않았으면 누락으로 판정하지 않고 `검토 필요`로 둔다.

### F9. 중복 제출 검사

| 항목 | 내용 |
| --- | --- |
| 비교 대상 | 같은 묶음 안의 서류끼리, 그리고 이전 청구 목록(F1 선택 입력) |
| 같은 서류로 보는 조건 | 요양기관 + 진료 기간 + 환자 + 납부한 금액이 모두 같다. 영수증 번호가 있으면 번호가 같은 것으로 충분 |
| 출력 | `DUPLICATE` 이슈. 겹치는 서류와 근거 |

- 재발행 영수증(같은 진료, 다른 발행일)도 같은 서류로 본다.
- 확정되지 않은 값이 조건에 끼면 `검토 필요`.

### F10. 오류 원인 분류와 결론 (핵심)

**이슈 원인**

| 원인 | 판단 근거 | 담당자 할 일 |
| --- | --- | --- |
| `READ_ERROR` 읽기 오류 의심 | F6에서 확정 실패 (`READ_CONFLICT`, `UNSTABLE_BASE`, `AMBIGUOUS_VALUE`, `LOW_OCR`) | 원본 이미지에서 표시된 칸만 확인 |
| `DOC_MISMATCH` 서류 불일치 | 값은 모두 확정됐고 영수증 안 검산식도 통과했는데, F7 문서 간 검증이 깨짐 | 병원에 정정·재발급 요청 |
| `DOC_MISSING` 서류 누락 | F8 | 고객에게 서류 추가 요청 |
| `DUPLICATE` 중복 제출 | F9 | 기존 청구와 대조 |
| `NEEDS_REVIEW` 기타 검토 필요 | `INTERNAL_MISMATCH`, `UNKNOWN_DOC`, `CROPPED`, `MISSING_FIELD` 등 | 이유를 보고 판단 |

**청구 묶음 결론**

| 결론 | 조건 |
| --- | --- |
| 심사 진행 가능 | 필수 필드가 모두 확정됐고, 이슈가 하나도 없다 |
| 보완 요청 | `DOC_MISMATCH`, `DOC_MISSING`, `DUPLICATE` 이슈만 있다 (모두 근거가 확실한 이슈) |
| 검토 필요 | `READ_ERROR` 또는 `NEEDS_REVIEW` 이슈가 하나라도 있다 |

- 결론이 `검토 필요`여도 보완 요청 이슈는 함께 보여준다.

### F11. 결과 리포트

청구 묶음마다 JSON 결과(§4.1)와 사람이 읽는 한 장짜리 요약을 낸다. 앱 완성도보다 **담당자가 바로 쓸 수 있는 정리**에 집중한다.

**요약 구성**

1. **결론 한 줄**: 예) "보완 요청 — 질병분류기호가 적힌 처방전 누락 1건"
2. **확정된 핵심 값**: 환자, 요양기관, 진료 기간, 진료비 총액, 환자부담 총액, 비급여 금액. 값마다 확정 근거(`agree` / `checksum: C1`)
3. **이슈 목록**: **차이 금액이 큰 순서**로 정렬. 원인, 관련 칸, 양쪽 값, 원문 위치(문서·페이지·셀)
4. **보완 요청 문구 초안**: 이슈마다 고객이나 병원에 보낼 한 문장. 예) "청구 금액이 3만 원을 넘어 질병분류기호가 적힌 처방전을 추가로 보내 주세요."
5. **원문 보기**: 이슈를 누르면 원본 이미지의 해당 칸에 표시

- 보완 요청 문구는 LLM(Instruct)으로 만들되, 이슈의 원인·서류명·금액만 넣고 새 사실을 더하지 않는다.

### F12. 검토 필요 처리

모든 단계에서 판단할 수 없으면 추측하지 않고 이유 코드를 붙여 넘긴다.

| 코드 | 단계 | 뜻 |
| --- | --- | --- |
| `CROPPED` | F2 | 문서 일부가 잘림 |
| `LOW_OCR` | F2·F6 | 해당 칸을 잘 읽지 못함 |
| `UNKNOWN_DOC` | F3 | 문서 종류가 애매함 |
| `MISSING_FIELD` | F6 | 두 경로 모두 값을 찾지 못함 |
| `READ_CONFLICT` | F6 | 두 경로 값이 다르고 검산으로도 못 고름 |
| `AMBIGUOUS_VALUE` | F6 | 두 값이 모두 검산식을 통과함 |
| `UNSTABLE_BASE` | F6 | 검산 기준 값이 흔들림 |
| `INTERNAL_MISMATCH` | F6 | 두 경로가 같은 값을 읽었는데 영수증 안 검산식이 깨짐 |
| `UNVERIFIED_INPUT` | F7·F8·F9 | 비교에 필요한 값이 확정되지 않음 |

- 금액은 절대 추측해서 채우지 않는다.

### F13. 정답지 대비 평가와 단계별 비교

심사·개발용. 명령 한 번으로 전체 케이스를 돌리고 리포트를 낸다.

**지표**

| 지표 | 계산 |
| --- | --- |
| 분류 정확도 | 문서 유형이 정답과 같은 비율 |
| 확정 값 정확도 | **확정한 값** 중 정답과 같은 비율. 높을수록 "믿고 넘긴 값"이 믿을 만하다는 뜻 |
| 자동 확정률 | 전체 필드 중 확정한 비율. 너무 낮으면 담당자 일이 줄지 않는다 |
| 이슈 탐지 | 정답 이슈 대비 정밀도·재현율 (원인 코드까지 같아야 맞음) |
| 결론 정확도 | 청구 묶음 결론이 정답과 같은 비율 |
| 재현성 | 같은 입력을 3번 돌렸을 때 결과가 모두 같은 비율 |

**단계별 비교 (설계 근거)**

같은 케이스로 구성을 바꿔 가며 잰다. 설계서와 발표에서 "왜 이렇게 짰는지"의 근거로 쓴다.

| 구성 | 보는 것 |
| --- | --- |
| ① 경로 B만, 검증 없음 | 틀린 값이 그대로 통과한 수 (기준선) |
| ② 경로 A + B 비교 | 두 경로 비교로 걸러진 오류 수 |
| ③ ② + 검산식 확정 | 검산으로 바로잡힌 수, 검토 필요로 넘어간 수 |
| ④ ③ + 문서 간 검증·원인 분류 | 원인을 정답과 같게 나눈 비율, 결론 정확도 |

## 3. 검산식

> 「국민건강보험 요양급여의 기준에 관한 규칙」 별지 제6호·제7호서식(2024. 7. 18. 개정)과 진료비 세부산정내역 서식(고시 제2018-21호) 기준이다. 세부산정내역 고시는 이후 개정 여부를 확인해야 한다(§9 Q2).

**영수증 칸 번호**

| 번호 | 칸 |
| --- | --- |
| ① ② ③ ④ | 합계 행의 본인부담금, 공단부담금, 전액본인부담, 비급여 |
| ⑤ | 상한액 초과금 |
| ⑥ ⑦ ⑧ | 진료비 총액, 공단부담 총액, 환자부담 총액 |
| ⑨ ⑩ ⑪ | 이미 납부한 금액, 납부할 금액, 납부한 금액 |

**영수증 금액 칸 (F6에서 값 확정에 사용, 오차 없음)**

| ID | 식 | 근거 |
| --- | --- | --- |
| C1 | ⑥ = ① + ② + ③ + ④ | 서식에 적힌 식 |
| C2 | ⑦ = ② + ⑤ | 서식에 적힌 식 |
| C3 | ⑧ = (① − ⑤) + ③ + ④ | 서식에 적힌 식 |
| C4 | ⑩ = ⑧ − ⑨ | 서식에 적힌 식 |
| C5 | ⑪ 합계 = 카드 + 현금영수증 + 현금 | 서식 구성에서 정리 |
| C6 | 납부하지 않은 금액 = ⑩ − ⑪ | 서식에 적힌 식 |

위 번호와 C1~C6은 제6호~제9호서식 기준이다. 다른 서식은 칸 번호와 식이 달라서 `form_no`에 따라 아래 식을 쓴다.

| 서식 | ID | 식 |
| --- | --- | --- |
| 제10호·제11호 약제비, 제12호 간이 외래 | P1 | ⑤ 총액 = ① + ② + ③ + ④ |
| | P2 | ⑥ 환자부담 총액 = ⑤ − ② |
| | P3 | 납부한 금액 합계 = 카드 + 현금영수증 + 현금 |
| 제12호의2 납입 확인서 | N1 | 줄마다 총액 = ① + ② + ③ + ④ |
| | N2 | 줄마다 본인부담 총액 = ② + ③ + ④ |

- 제10호·제11호·제12호에는 상한액 초과금, 이미 납부한 금액, 납부할 금액 칸이 없다.
- **제12호의2는 ①이 공단부담금, ②가 본인부담금이다.** 진료비 영수증과 번호가 반대다.
- 그래서 코드와 JSON은 칸 번호를 쓰지 않고 **뜻으로 정한 키**(`copay_total`, `insurer_total` 등)를 쓴다.

**항목 합계 (참고 검사, 값 확정에는 쓰지 않음)**

| ID | 식 | 허용 범위 |
| --- | --- | --- |
| S1 | 영수증 각 열의 항목 행 합 ≈ 합계 행 | 끝수처리 때문에 다를 수 있다. 초기값 ±100원 (§9 Q10) |
| S2 | 세부내역서 각 열의 항목 줄 합 = 계 | 오차 없음 |
| S3 | 세부내역서 각 열의 계 + 끝수처리 조정금액 = 합계 | 오차 없음 |

허용 범위를 벗어나거나 오차 없는 식이 깨지면 `INTERNAL_MISMATCH`로 둔다.

- 금액은 원 단위 정수로 비교한다.
- 금액 칸 검산식(C1~C6)은 **값을 고르는 데**, 서류 사이 규칙(F7의 X1·X2)은 **불일치를 판정하는 데** 쓴다. 둘을 섞지 않는 것이 "읽기 오류 vs 서류 불일치"를 나누는 핵심이다.
- C1은 2024년 서식의 샘플에서, C3은 샘플에서 맞는 것을 확인했다. 수납금액을 원 단위로 끊는 양식도 있어 C4는 실제 서류로 더 확인한다(§9 Q10).

| `rows[]` | 항목 행별 본인부담금·공단부담금·전액본인부담·비급여 | S1 |
| `copay_total` | ① 본인부담금 합계 | C1·C3·S1 |
| `insurer_total` | ② 공단부담금 합계 | C1·C2·S1 |
| `full_copay_total` | ③ 전액본인부담 합계 | C1·C3·S1 |

| `cap_excess` | ⑤ 상한액 초과금 | C2·C3 |
| `bill_total` | ⑥ 진료비 총액 | C1 |
| `insurer_grand_total` | ⑦ 공단부담 총액 | C2 |
| `patient_total` | ⑧ 환자부담 총액 | C3·C4 |

| `unpaid` | 납부하지 않은 금액 | C6 |

항목 행 이름은 서식 그대로 쓴다: 진찰료, 입원료(1인실, 2·3인실, 4인실 이상), 식대, 투약 및 조제료(행위료, 약품비), 주사료(행위료, 약품비), 마취료, 처치 및 수술료, 검사료, 영상진단료, 방사선치료료, 치료재료대, 재활 및 물리치료료, 정신요법료, 전혈 및 혈액성분제제료, CT·MRI·PET·초음파 진단료, 보철·교정료, 제증명수수료, 선별급여, 65세 이상 등 정액, 정액수가(요양병원), 정액수가(완화의료), 질병군 포괄수가, 기타. 선택항목은 병원에 따라 추가하거나 뺄 수 있다.

약제비·간이 영수증도 금액 칸은 같은 키를 쓴다. 총액은 `bill_total`, 환자부담 총액은 `patient_total`이다. 세부내역서, 처방전, 납입 확인서는 공통 필드에 더해 서류별 고유 필드를 같은 방식으로 정한다(§9 Q3).

### 4.2 정답지

분석 결과와 **같은 키와 형식**으로 쓴다. 경로별 값은 없고 정답 값만 둔다.

```jsonc
{
  "case_id": "case_14",
  "category": "trap",                    // simple | variety | combined | low_quality | trap
  "conclusion": "request_supplement",
  "documents": [{ "file_name": "receipt.jpg", "type": "receipt" }],
  "fields": [
    { "file_name": "receipt.jpg", "key": "copay_total", "value": 35000, "evidence_text": "35,000" }
  ],
  "issues": [
    { "cause": "DOC_MISSING", "rule": "D2" }
  ]
}
```

**형식 규칙**

- 금액: 쉼표 없는 정수(원)
- 날짜: `YYYY-MM-DD`
- 판정·원인·결론: 위에 정한 enum 값만
- 값이 서류에 없으면 `null`
- 정답지는 두 사람이 따로 쓰고, 다른 부분만 맞춘다
- 정답지가 스키마에 맞는지 검사하는 스크립트를 둔다

## 5. 케이스 구성 (30개)

| 양식·문맥 다양성 | 6 | 제6호(표 선 있음), 제7호(괄호 칸 인쇄), 제8호(한방, 표 선 있음), 제9호(한방, 괄호 칸 인쇄), 제10·11호(약국), 제12호(수기 간이), 제12호의2(납입 확인서). 선택항목 추가·생략, 같은 항목의 다른 이름 |

| 예외·함정 | 7 | 아래 표 |

**예외·함정 케이스**

| 케이스 | 기대 결과 |
| --- | --- |
| 세부내역서 합계가 영수증과 다름 | `DOC_MISMATCH` (X1·X2) |
| 서류끼리 환자 이름이 다름 | `DOC_MISMATCH` (X3) |
| 통원 5만 원인데 처방전 없음 | `DOC_MISSING` (D2) |
| 같은 영수증 재발행본이 같이 들어옴 | `DUPLICATE` |
| 카드 전표만 있고 영수증 없음 | `DOC_MISSING` (D1) |
| 흐린 숫자를 두 경로가 다르게 읽음 | 검산으로 확정 또는 `READ_ERROR` |
| **헷갈리지만 정상**: 상한액 초과금이나 끝수처리 때문에 합계가 달라 보임 | 이슈 없음 (오탐하지 않아야 함) |

- 실제 진료 영수증은 민감한 의료 정보라 **법정 서식에 가상 값을 채워 만든다.** 실제 문서를 쓰면 이름·번호를 모두 가린다.
- 케이스마다 어떻게 만들었는지(실제 / 가상 / 실제를 고침)를 정답지에 적는다.

## 6. 비기능 요구사항

## 8. 발표 핵심 장면

1. 흐린 영수증에서 경로 B가 본인부담금을 36,000원으로 읽는다.
2. 경로 A는 35,000원. 검산식 C1로 35,000원이 확정되고, 근거가 표시된다.
3. 값이 모두 확정된 뒤 세부내역서와 비교하니 비급여 합계가 42,000원 다르다 → **서류 불일치**, 병원 정정 요청 문구가 나온다.
4. 같은 30개 케이스로 ①~④ 구성을 비교한 표를 보여준다. 검증 단계를 더할수록 "믿고 넘긴 값"의 정확도가 올라간다.
